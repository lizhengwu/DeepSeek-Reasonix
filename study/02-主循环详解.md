# Reasonix 主循环：从发送消息到完成回复

> 本文追踪当用户发送一句话后，系统内部完整的执行链路。

## 一、总览：完整调用链

```
```

## 二、关键时间点：什么时候访问 LLM？

```
执行前准备 (runTurnWithRaw)
    ├── maybeSessionStart()    ← ❌ 没调LLM，纯本地逻辑
    ├── maybeAutoPlan()        ← ❌ 没调LLM，本地启发式打分
    ├── Compose(input)         ← ❌ 没调LLM，拼接消息
    ├── 钩子 UserPromptSubmit  ← ❌ 没调LLM
    │
    ├── ════════════════════════════════════════════
    │   🔥 第一次访问 LLM 从这里开始
    ├── c.runner.Run(ctx, input)
    │       │
    │       ▼  Agent.Run 循环:
    │           step=0: stream()  → 调 LLM ──→ 返回文本+3个工具调用
    │                   executeBatch() → 执行3个工具
    │                   maybeCompact()
    │           step=1: stream()  → 再调 LLM ──→ 返回文本+1个工具调用
    │                   executeBatch() → 执行工具
    │           step=2: stream()  → 再调 LLM ──→ 只返回文本 (最终答案)
    │                   return nil  ← 循环结束
    │
    ├── ════════════════════════════════════════════
    │   从这之后 LLM 不再被调用（纯本地逻辑）
    ├── plan mode 审批门（如果开了规划模式）
    └── 批准后可能再触发一个子 turn (又一轮 Run)
```

**结论：** 执行前准备阶段**完全不碰 LLM**。第一次访问 LLM 发生在 `runTurnWithRaw` 第 370 行 `c.runner.Run(ctx, input)` 进入 Agent 循环之后。Agent 每轮循环都调一次 LLM，直到 LLM 只返回文本（最终答案）为止。

## 三、步骤详解

### 第1步：`Controller.Send` — 入口

**文件：** `internal/control/controller.go:314`

```go
func (c *Controller) Send(input string) {
    c.SendWithRaw(input, input)
}

func (c *Controller) SendWithRaw(input, raw string) {
    c.runGuarded(func(ctx context.Context) error {
        return c.runTurnWithRaw(ctx, input, raw)
    })
}
```

关键行为：
- **异步执行** — `runGuarded` 在新 goroutine 中执行，不阻塞前端
- **并发保护** — 同一时刻只允许一个 turn 运行（如果已在运行则直接 return）
- **TurnDone** — turn 结束时自动发射 `event.TurnDone`，前端据此更新界面

```go
func (c *Controller) runGuarded(body func(ctx context.Context) error) {
    c.mu.Lock()
    if c.running { c.mu.Unlock(); return }  // ← 并发保护
    ctx, cancel := context.WithCancel(context.Background())
    c.cancel = cancel
    c.running = true
    c.mu.Unlock()

    go func() {
        defer cancel()
        err := body(ctx)
        c.mu.Lock()
        c.running = false
        c.mu.Unlock()
        c.sink.Emit(event.Event{Kind: event.TurnDone, Err: explainError(err)})
    }()
}
```

### 第2步：`runTurnWithRaw` — Turn 编排

**文件：** `internal/control/controller.go:348`

这是整个 turn 的编排层，**此时 LLM 还没被访问**，全是本地逻辑：

#### 2a. `maybeSessionStart()`
首次 turn 时触发 `SessionStart` 钩子（一次性）。

#### 2b. `maybeAutoPlan()`
**文件：** `internal/control/auto_plan.go:36`

判断当前输入是否需要自动进入 **plan mode**（先规划再执行）：
1. 如果 `auto_plan` 已关闭、已在 plan mode、或 bypass 模式 → 跳过
2. 用启发式算法 `autoPlanScore()` 给输入打分
3. 可选的 LLM 分类器进一步判断（但那是可选的小模型快速判断，不是主 LLM）
4. 如果得分够高 → 自动打开 `SetPlanMode(true)`，并提示用户

这样像"帮我重构 main.go"这种复杂请求会自动先走规划流程，而"这个函数是做什么的"这种简单问题直接进入执行。

#### 2c. `Compose(input)` — 装配最终消息
**文件：** `internal/control/input.go:18`

```go
func (c *Controller) Compose(text string) string {
    // 1) 如果 plan mode 开着 → 前面追加 PlanModeMarker
    // 2) 如果有 pending 记忆更新 → 包装成 <memory-update> 追加
    // 3) 如果有完成的后台任务 → 包装成 <background-jobs> 追加
    return text
}
```

设计要点：
- **PlanModeMarker** 以用户消息而非 system prompt 方式携带，**不破坏缓存稳定性**
- 记忆更新和后台任务结果也走"turn tail"，同样不触及缓存前缀

#### 2d. 钩子：`UserPromptSubmit`

如果开启了 hook 系统，在这里检查是否有 hook 拦截该输入。

#### 2e. `c.runner.Run(ctx, input)` — 🔥 第一次访问 LLM！

将装配好的输入交给 Agent，Agent.Run 内部通过 `stream()` 调用 `provider.Stream()` — 这才是真正发出 HTTP 请求到 LLM API：

```
runTurnWithRaw 第370行:
    if err := c.runner.Run(ctx, input); err != nil { ... }
                           │
                           ▼
                Agent.Run 第372行:
                    a.session.Add(用户消息)
                    for step := 0; ; step++ {
                        a.stream()         → 🔥 调 LLM API
                        a.executeBatch()   → 执行工具
                        a.maybeCompact()
                    }
```

#### 2f. Plan Mode 审批门（LLM 调用结束后）

如果 turn 结束且当前在 plan mode（此时 LLM 已经完成了它的回答）：
1. 提取 AI 生成的计划文本
2. `requestApproval()` 向用户展示计划并等待审批
3. 批准 → 关闭 plan mode，种子化任务列表，自动批准写入，用 `planApprovedMessage` 驱动**又一个子 turn**（又一轮 Agent.Run）
4. 拒绝 → 保持 plan mode，等待下一轮修改

### 第3步：`Agent.Run` — 核心循环（第一次调 LLM 的地方）

**文件：** `internal/agent/agent.go:367`

`Agent.Run` 在第 370 行被 `runTurnWithRaw` 调用，这是**第一次真正访问 LLM API**。

关键理解：**每次 `stream()` 调用 LLM，LLM 在一次响应中既可以返回文本，也可以同时返回 0~N 个工具调用。** 这是 LLM 的 native 能力（function calling / tool use）。

```go
func (a *Agent) Run(ctx context.Context, input string) error {
    a.session.Add(provider.Message{Role: provider.RoleUser, Content: input})
    //                        ↑ 先把用户消息存进历史

    for step := 0; a.maxSteps <= 0 || step < a.maxSteps; step++ {
        // ── 🔥 调 LLM ──
        text, reasoning, signature, calls, usage, err := a.stream(ctx, step+1)
        //    ↑ 文本    ↑ 推理过程   ↑ 签名   ↑ 工具调用列表  ↑用量

        // ── 记录用量 ──
        // 发出 Usage 事件给前端显示 token 消耗

        // ── 追加 Assistant 消息 ──
        a.session.Add(provider.Message{
            Role:    provider.RoleAssistant,
            Content: text,
            ReasoningContent: reasoning,
            ToolCalls: calls,     // ← 工具调用也存入历史
        })

        // ── 无工具调用 → LLM 给出了最终答案 ──
        if len(calls) == 0 {
            if reason := a.finalReadinessFailure(); reason != "" {
                continue  // 完整性检查没通过，要求 LLM 补全
            }
            return nil  // ◄── Turn 结束！
        }

        // ── 执行 LLM 要求的工具调用 ──
        results := a.executeBatch(ctx, calls)
        for i, call := range calls {
            a.session.Add(provider.Message{
                Role: provider.RoleTool,
                Content: results[i],
                ToolCallID: call.ID,
                Name: call.Name,
            })
        }

        // ── token 接近窗口上限？压缩历史 ──
        a.maybeCompact(ctx, usage)

        // ── 回到循环开头，再调 LLM ──
        // 这次把上轮的工具执行结果也传入，LLM 据此决定下一步
    }
    // maxSteps 耗尽时暂停
    return fmt.Errorf("paused after %d tool-call rounds", a.maxSteps)
}
```

#### 图解：一次典型的多轮交互

```
                         每次 stream() 都调一次 LLM
                              │
Agent.Run 循环              stream()
 ────────────────────────────────────────────────────>
     │                        │                        │
     │   step 0               │  step 1                │  step 2
     ▼                        ▼                        ▼
 ┌──────────────┐      ┌──────────────┐         ┌──────────────┐
 │ LLM 收到:    │      │ LLM 收到:    │         │ LLM 收到:    │
 │ 用户消息     │      │ 文本回复     │         │ 工具结果     │
 │ + 工具定义   │      │ + read_file  │         │ + grep 结果  │
 │              │      │ + grep       │         │ + 自己的推理  │
 │ 返回:        │      │ + ls         │         │              │
 │ 文本分析     │      │              │         │ 返回:        │
 │ + read_file  │ ──►  │ 返回:        │ ──►     │ 最终答案     │
 │ + grep       │      │ 文本分析     │         │ "重构完成"   │
 │ + ls         │      │ + edit_file  │         │              │
 └──────┬───────┘      └──────┬───────┘         └──────────────┘
        │                     │
        ▼                     ▼
  executeBatch(3个工具)  executeBatch(1个工具)
    ├── read_file  ──并行──    └── edit_file
    ├── grep       ──并行──
    └── ls         ──并行──
```

**关键点：**
- 每次 `stream()` 都是**一次完整的 LLM API 调用**，不是分步的
- LLM 一次可以返回**多个工具调用**（三个、五个甚至更多）
- 工具执行结果**追加到 session 历史**，再调用 `stream()` 时一起发给 LLM
- LLM 根据执行结果决定下一步：继续调工具？还是给出最终答案？
- 直到某次 `stream()` 返回**0 个工具调用**，循环结束

#### LLM 到底怎么在一次响应里返回多个工具调用？

这是 LLM 协议层的功能。以 OpenAI 兼容 API 为例，一个 SSE 事件流可以同时包含文本和多个工具调用：

```json
// SSE 流中的几个事件（简化）
data: {"choices":[{"delta":{"content":"我来看看这个文件"}}]}

data: {"choices":[{"delta":{"tool_calls":[{"index":0,"id":"call_1",
       "function":{"name":"read_file","arguments":"{\"path\":\"main.go\"}"}}]}}]}

data: {"choices":[{"delta":{"tool_calls":[{"index":1,"id":"call_2",
       "function":{"name":"grep","arguments":"{\"pattern\":\"func\"}"}}]}}]}

data: {"choices":[{"delta":{"tool_calls":[{"index":2,"id":"call_3",
       "function":{"name":"ls","arguments":"{}"}}]}}]}}

data: {"usage":{"prompt_tokens":1000,...}}
```

Provider 层（`internal/provider/openai/openai.go:264-285`）解析这个流：
- **流式逐行解析**：每个 `delta` 块可能包含文本、推理内容、或工具调用的分片
- **工具调用按 index 聚拢**：同一个 index 的多个分片合并成一个完整的 `ToolCall`
- 流结束后，**一次性返回所有收集到的工具调用列表**给 Agent
- Agent 拿到 `calls` 列表，全部执行，结果塞给 LLM 下一轮

其他供应商（Anthropic）也是类似的机制，只是事件格式不同。

### 第3A步：`stream()` — 流式 LLM 调用

**文件：** `internal/agent/agent.go:504`

```go
func (a *Agent) stream(ctx context.Context, turn int) (...) {
    ch, err := a.prov.Stream(ctx, provider.Request{
        Messages: a.session.Messages,     // 全部历史消息
        Tools:    a.tools.Schemas(),      // 工具定义 schemas
    })
    // 接收事件流，按类型分派
    for chunk := range ch {
        switch chunk.Type {
        case ChunkReasoning:     // 推理过程 → 发射 Reasoning 事件
        case ChunkText:          // 文本 → 发射 Text 事件
        case ChunkToolCallStart: // 工具调用开始 → 发射 ToolDispatch(partial)
        case ChunkToolCall:      // 完整工具调用 → 收集到 calls 列表
        case ChunkUsage:         // 用量信息 → 记录
        case ChunkError:         // 错误 → 返回
        }
    }
    // 流结束后：发射 Message 事件 (完整文本+推理)
    return text, reasoning, signature, calls, usage, nil
}
```

关键行为：
- 推理过程（Reasoning）实时流式发射，用户可以看到 AI "正在思考..."
- 工具调用（ToolCall）在参数收集完毕后才传给调用方
- 每个 chunk 的文本也是实时发射，做流式渲染
- 可选 `PostLLMCall hook` 转换推理文本

### 第3D步：`finalReadinessFailure()` — 最终答案完整性检查

**文件：** `internal/agent/agent.go:434`

在 AI 准备给出最终答案（无工具调用）前，检查：
1. ✅ 是否有未完成的 todo 项
2. ✅ 是否调用了 `complete_step` 来验收每个步骤
3. ✅ 如果配置了项目验证命令（如 `go test`、`npm run lint`），是否已执行
4. ✅ 在 plan mode 之外，是否有写入操作但未完成验收

### 第3E步：`executeBatch()` — 批量执行工具

**文件：** `internal/agent/agent.go:597`

```go
func (a *Agent) executeBatch(ctx context.Context, calls []provider.ToolCall) []string {
    // 1) 为每个工具调用发射 ToolDispatch 事件（按调用顺序）
    // 2) partitionToolCalls: 将调用分组
    //    - 连续的只读工具 → 并行执行
    //    - 写入工具 → 串行执行（保持顺序）
    //    - complete_step/todo_write → 串行（依赖前序结果）
    // 3) 每组执行后，按原序发射 ToolResult 事件
    // 4) applyStormBreaker: 风暴打断器检查
    return results
}
```

### 第3F步：`maybeCompact()` — 自动压缩

**文件：** `internal/agent/compact.go:63`

1. 将会话历史中间部分压缩为一段摘要

## 四、核心问题详解

### Q1：LLM 怎么知道有哪些工具可用？

**答案：工具定义作为 JSON Schema 随每次请求一起发出。**

每次 `stream()` 调用 LLM 时（`agent.go:508-511`）：

```go
ch, err := a.prov.Stream(ctx, provider.Request{
    Messages: a.session.Messages,
    Tools:    a.tools.Schemas(),    // ← 全部工具定义在这里
})
```

`a.tools.Schemas()` 遍历注册表，为每个工具生成 `ToolSchema`：

```go
type ToolSchema struct {
    Name        string          `json:"name"`        // 工具名，如 "edit_file"
    Description string          `json:"description"` // 自然语言描述
    Parameters  json.RawMessage `json:"parameters"`  // JSON Schema 定义参数
}
```

这些被序列化后直接塞进 API 请求的 `tools` 字段（`openai.go:165-171`）：

```json
// 实际上发到 LLM API 的请求（简化）：
{
  "model": "deepseek-chat",
  "messages": [...],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "edit_file",
        "description": "Replace an exact string in a file with another...",
        "parameters": {
          "type": "object",
          "properties": {
            "path":        { "type": "string", "description": "File path" },
            "old_string":  { "type": "string", "description": "..." },
            "new_string":  { "type": "string", "description": "..." }
          },
          "required": ["path", "old_string", "new_string"]
        }
      }
    },
    {
      "type": "function",
      "function": {
        "name": "bash",
        "description": "Execute a command in the shell...",
        "parameters": { ... }
      }
    }
    // ... read_file, grep, glob, write_file, web_fetch 等所有工具
  ]
}
```

这是 **OpenAI 兼容 API 的标准 `function calling` / `tool use` 机制**。LLM 原生理解这个 `tools` 数组——它会在训练时就被教会：看到工具定义→按需调用。

每个内置工具在注册时都定义了 `Name()`、`Description()` 和 `Schema()`：

```go
// editfile.go
func (editFile) Name() string { return "edit_file" }

func (editFile) Description() string {
    return "Replace an exact string in a file with another. old_string must occur exactly once..."
}

func (editFile) Schema() json.RawMessage {
    return json.RawMessage(`{"type":"object","properties":{...}}`)
}
```

**所以 LLM 知道工具有两重保障：**
1. **API 协议层**：`tools` 数组显式告诉 LLM"这些函数你可以调用"
2. **System Prompt 层**：system prompt 也说明了"Use the provided tools to read and write files and run shell commands"

### Q2：LLM 怎么知道什么时候"完事"了？怎么让它停？

**答案：System Prompt 没有专门说"完事了就返回文本"——这是 LLM 原生协议行为。**

关键在于 LLM API 的协议设计：

#### LLM 每次响应只有两种结束方式

| 结束方式 | 协议含义 | Agent 行为 |
|---------|---------|-----------|
| `finish_reason: "tool_calls"` | LLM 说要调工具 | Agent 执行工具，再调 LLM |
| `finish_reason: "stop"` | LLM 说回答完了 | Agent 认为 turn 结束 |

**不需要在 prompt 里告诉它"完事就返回文本"**——LLM 在训练时就学会了：

> 如果任务还需要更多信息 → 调工具
> 如果任务完成了 → 直接输出文本回答，不调工具

Agent 的判断逻辑很简单（`agent.go:400-411`）：

```go
if len(calls) == 0 {
    // LLM 没有要求调工具 → 认为它给出了最终答案
    return nil
}
// 有工具调用 → 执行，再继续循环
```

#### 完整的 system prompt 是什么

```go
const DefaultSystemPrompt = `You are Reasonix, a coding agent focused on executing code tasks.
Use the provided tools to read and write files and run shell commands.
Principles: understand the request before acting; verify with tools instead of
guessing; keep changes minimal and correct; briefly summarize what you did.
When the request leaves a real choice to the user — which approach or library,
the scope, or a consequential or ambiguous decision — call the ask tool to offer
2-4 concrete options rather than guessing or burying the question in prose. Skip
it when there's an obvious default; don't ask just to confirm.
For multi-step work, track progress with the todo_write tool: lay out the steps,
keep exactly one in_progress, and flip each to completed as you finish it — update
the list as you go, not just at the end.
In plan mode the harness blocks writer tools: do read-only research, then write a
concise plan as your reply and stop. The user is asked to approve before anything
is changed; once approved, work through the steps, updating the task list as you go.`
```

注意它没有"完事就别调工具"这样的指令。这是 LLM 的**原生能力**——function calling 协议本身就是这么设计的：LLM 要么调工具，要么给文本回答，二选一。

#### 打个比方

这就像一个人类程序员和你说：
- "我有这些工具：read_file、bash、edit_file……"（tools 数组）
- "你是一个编码 agent"（system prompt）

你不会问"什么时候该停"——你自然知道：
- 需要信息时 → 调 `read_file`
- 需要检查时 → 调 `bash("go test")`
- 搞定了 → 直接说"搞定了"

LLM 也一样，这是它训练时就学会的。

## 五、关键设计点

| 设计点 | 说明 |
|--------|------|
| **异步 turn** | `runGuarded` 启动 goroutine，前端不阻塞 |
| **并发保护** | 同一时刻只允许一个 turn 运行 |
| **缓存稳定性** | plan marker、记忆更新都走 turn tail，不破坏 system prompt 缓存 |
| **并行工具执行** | 连续的只读工具并行执行，写工具串行保持顺序 |
| **自动规划** | `maybeAutoPlan` 用启发式+分类器判断是否需要先规划 |
| **完整性检查** | 最终答案前检查 todo、测试、验证命令是否完整 |
| **自动压缩** | 接近窗口上限时自动压缩历史 |
| **Plan 审批门** | 规划模式下需要用户批准计划后才执行 |
| **风暴打断** | 工具执行风暴检测与中断 |
